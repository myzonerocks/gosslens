---
title: The lens format
description: A declarative bundle the runtime executes. Lenses don't run code, and every field gets validated before a frame touches it.
---

A lens is a bundle: a `manifest.json` plus whatever it draws with, which is
usually shaders, glTF assets, LUTs and textures.

Nothing in a lens executes. The manifest describes nodes, parameters and
triggers, and the runtime does the work. That's what makes it safe to load one
from somewhere you don't control.

## A whole manifest

This is a complete, working lens:

```json
{
  "glf": "1.0",
  "id": "goss.reference.lip-tint",
  "version": "1.0.0",
  "display_name": "Lip Tint",
  "engine_compat": ">=0.5",
  "capabilities": ["face"],
  "parameters": [],
  "nodes": [
    {
      "id": "tint",
      "type": "tint.pass",
      "inputs": { "frame": "camera" },
      "params": {},
      "tint": { "color": [0.8, 0.1, 0.3], "opacity": 0.6, "mask": "lips" }
    }
  ],
  "triggers": []
}
```

`glf` is the format version. `engine_compat` is the range of engines this lens
is willing to run on, and the runtime refuses it outside that range instead of
drawing something approximate.

## What a lens asks for

`capabilities` is the lens saying what it needs: `face`, `hands`,
`segmentation`, `world`. A build without one refuses the lens up front, which
is a much better failure than a lens that loads and quietly draws nothing.

It's the lens-side mirror of the engine's own [capability
bits](/docs/concepts/capabilities).

## Nodes

Each node has an `id`, a `type`, its `inputs` wired to other node ids or to
`camera`, and its `params`.

You'll see `model.gltf` for geometry, `tint.pass`, `shader.pass`, `warp.pass`,
`outline.pass`, `grade.pass`, `smooth.pass` and `stylize.pass` for image
passes, and `sprite.2d` and `text.2d` for overlays. An `ml.infer` node is how
[your own model](/docs/build/models) joins the graph.

Whatever nodes a lens brings get merged into the [frame
graph](/docs/concepts/graph) and scheduled along with everything else, once.

## Parameters

```json
{ "name": "spin_w", "type": "float", "default": 1.0, "min": 0.0, "max": 1.0 }
```

Parameters are a lens's public surface. Your app can set them at runtime, and
the runtime enforces the bounds rather than trusting whatever you passed.

## Triggers

A trigger binds a condition to an action. The condition is an expression over
signals the engine already measures, and the action is something the runtime
knows how to do.

```json
{
  "triggers": [
    {
      "when": "face.present",
      "action": { "kind": "play_sound", "target": "pop" }
    },
    {
      "when": "timer('x') >= 0.3",
      "action": {
        "kind": "param_ramp",
        "target": "spin_w",
        "to": 0.0,
        "duration_ms": 100,
        "curve": "ease_in_out_quad"
      }
    }
  ]
}
```

Signals include things the engine tracks, like `face.present` and
`device.in_volume`, plus `timer('name')` for time since a named moment.

Actions include `param_set`, `param_ramp`, `play_animation` and `play_sound`.
Your app can raise its own events into this, so your product's moments can
drive a lens without the lens knowing anything about your code.

## Lenses are untrusted content

No lens runs arbitrary code. Shaders compile through the pinned toolchain under
resource limits, manifests are size and depth limited, and a malformed bundle
gets refused instead of partly applied. We fuzz both the manifest parser and
the shader input.

## Loading one

```c
goss_session_activate_lens(session, manifest, manifest_len);
goss_session_activate_lens_from_directory(session, path, path_len);
```

Develop against the directory form, because then you can edit the bundle in
place and see it change.
