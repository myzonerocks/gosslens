---
title: Writing your own SDK
description: Everything a new binding has to get right, in the order it has to get it right, for a language the shipped SDKs do not cover.
---

The shipped SDKs are thin. Every one of them opens the same header, calls the
same symbols in the same order, and adds nothing the core could have done
itself. That is deliberate: it means a binding for a language nobody has
written yet is a known quantity rather than a research project.

This page is the whole job. Work through it in order and the result will behave
like the SDKs that ship with the engine, because it will be doing the same
things they do.

## What you are binding to

One header, `gosslens.h`. It is C99 and includes nothing beyond `stdint.h`,
`stddef.h` and `stdbool.h`, so any language with a C foreign function interface
can reach it without a C++ runtime, exceptions, or a build of its own.

Everything that crosses the boundary is one of three things: an opaque handle,
a plain-data descriptor with a fixed layout, or a status code. There is no
inheritance, no callback into your allocator, no ownership you did not ask for.

<Note>
If your language can call `dlopen` and read a struct field at a known offset,
it can host the engine. Nothing further is required of it.
</Note>

## Step one: check the version, and refuse

`goss_abi_version` returns a single `uint32_t`: the major in the high sixteen
bits, the minor in the low sixteen. It is safe from any thread and must be the
first call your binding makes.

```c
uint32_t version = goss_abi_version();
if ((version >> 16) != GOSS_ABI_MAJOR) {
    /* Refuse. Do not continue, do not degrade, do not call anything else. */
    return GOSS_ERROR_ABI_MISMATCH;
}
```

A major mismatch means the layouts your binding was generated against are not
the layouts the library has. Continuing reads the wrong bytes at the wrong
offsets and the failure surfaces somewhere unrelated, hours later.

The minor moves whenever an operation is added or a struct grows a field. A
higher minor than you were built against is safe: the symbols you know are
still where they were. A lower minor means the library predates a call you may
make, so look up anything optional before you rely on it.

`goss_abi_check` does the same comparison inside the library and returns a
status, which is the easier call to wire into a binding that already has error
plumbing.

## Step two: ask what the build can do

Two libraries can share a filename, a version and a symbol table, and still
differ in what they actually compute. A stub build answers every call and does
no real work, which is exactly what a continuous integration machine with no
camera wants and exactly what an application must not ship against silently.

`goss_capabilities` returns a bitfield. Read it once, keep it, and gate every
optional path on it.

```c
uint64_t caps = goss_capabilities();
bool can_track = (caps & GOSS_CAP_TRACKING) != 0;
bool can_segment = (caps & GOSS_CAP_SEGMENTATION) != 0;
```

Surface the bitfield to your users rather than hiding it. An application that
can see the engine has no tracking compiled in can say so; one that cannot see
it reports a camera bug instead.

## Step three: the lifecycle, and who owns what

Ownership is in the name and there are no exceptions to it. Every `create` has
a `destroy`. Every `acquire` has a `release`. A function that can fail returns
`goss_status`; there is no errno and nothing throws.

```c
goss_engine *engine = NULL;
goss_engine_config engine_config = { .texture_pool_capacity = 8 };
goss_status status = goss_engine_create(&engine_config, &engine);
if (status != GOSS_OK) return status;

goss_session *session = NULL;
goss_session_config session_config = { .frame_budget_us = 8000 };
status = goss_session_create(engine, &session_config, &session);
```

A session holds its engine. Destroy sessions before the engine they came from,
and make that structural rather than documented: in a language with
deterministic destruction, have the session object keep a strong reference to
the engine object, so the engine cannot be collected out from under a session
that is still drawing.

Zero means "the engine chooses" in both configs. Pass zeroed structs until you
have measured a reason not to.

## Step four: the thread rule

An engine and its sessions are confined to the thread that created them, called
the graph thread. A function is callable from another thread only when the
header says it is any-thread, as `goss_abi_version` does.

This is the rule most new bindings get wrong, because most languages make it
easy to break. A garbage collector that finalises on its own thread will call
`destroy` from the wrong one. An async runtime that resumes a continuation
wherever a worker is free will submit a frame from the wrong one.

Pin it explicitly:

- Give the binding one owned thread, or require the caller to name theirs.
- Record the thread identity at creation and assert it on every call in debug
  builds. The assertion costs nothing in release and saves whole afternoons.
- Never let a finaliser call into the engine. Have it post the destroy to the
  graph thread instead.

<Warning>
A call from the wrong thread does not reliably crash. It corrupts the pool's
bookkeeping and the symptom appears several frames later as a texture that
belongs to somebody else.
</Warning>

## Step five: structs, by layout and nothing else

Descriptors are `extern` structs with explicit padding, and their layout is
static-asserted in the engine's own tests. Your binding has to agree with that
layout byte for byte.

Generate the declarations rather than typing them. Every shipped SDK derives
its structs from the header, which is why none of them has ever disagreed with
it. If your language has no generator, write a test that compares your computed
offsets against the sizes the engine reports, and run it in continuous
integration rather than once.

Vectors cross by pointer. A position, a quaternion, a matrix or a colour is
passed as a pointer to a fixed-size array, never spread into separate float
parameters. This is an ABI hazard rather than a style preference: past the
eighth float argument the x86_64 calling convention spills to the stack, and a
caller and callee compiled by different toolchains can disagree about that
layout. Passing the aggregate keeps every scalar in a register and marshals
identically everywhere.

A struct only ever grows at its end, behind a size field. Read the size the
engine reports before touching a field your build added.

## Step six: frames, without copying

The whole point of the engine is that a camera frame reaches it without a
round trip through your language's heap. How that works is platform shaped, and
your binding should expose the platform path first and the copy path second:

- Where the platform has a hardware buffer or a shared texture, import it and
  submit the handle.
- Where it does not, submit the planes and let the engine stage them.
- Offer a copying call for correctness while bringing a platform up, and mark
  it as the slow path in your own documentation so nobody ships on it.

Reuse the buffers you allocate. A per-frame allocation in a binding is a
per-frame allocation in the product, and it is the first thing to show up in a
thermal profile.

## Step seven: reading the record back

Perception comes back as a snapshot the caller asks for, not as a callback the
engine fires. Ask once per frame, after submitting, and hand your users an
immutable value.

A JSON form exists and is the right first move for a new binding: it is stable,
it is easy to assert against, and it gets a working end-to-end path in an
afternoon. Move to the packed form once the shape is proven and you want the
allocation back.

## Step eight: events, drained not polled

The engine keeps a ring of events. A caller drains it and is told how many were
missed since the last drain. Surface that number rather than swallowing it: a
missed count that climbs is the clearest early signal that the host is not
keeping up, and an application that cannot see it has no way to react.

Do not wrap the drain in a thread that spins. Drain it on the frame you already
have.

## Step nine: prove it, the same way the others are proved

A binding is not finished when it runs. It is finished when it agrees with the
other bindings about what the engine said. Run the same program through your
binding and through the C one, and compare the records field by field. See
[proving a binding](/docs/binding/conformance) for what that suite looks like
and what it has to cover.

## The shape of a good binding

Everything above comes down to one rule: the binding translates and does
nothing else.

If your binding smooths a jittery landmark, caches a record, retries a failed
call, or decides which capability to use, then the behaviour of the product now
depends on which language the application happens to be written in. That is the
failure this architecture exists to prevent. Features belong in the core, where
every caller gets them at once. A binding that needed a feature has found a
hole in the core, and the fix is to say so rather than to patch it locally.
