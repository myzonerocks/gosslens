---
title: Agents and MCP
description: The same engine, reachable by a model over stdio, with the tools it exposes and the scope that bounds them.
---

An agent is a first-class caller rather than a feature bolted on. The engine
ships an MCP server: one static binary speaking JSON-RPC over stdio across the
same C ABI every SDK uses, so a model can open a camera or a screen, ask what
is in frame, and draw back into it with no runtime to install.

```bash
zig build mcp
```

The tools answer from the engine itself. A tool whose precondition is missing
names that one precondition rather than returning a generic refusal, and the
engine and its session come up on the first call that needs one.

## The tools

**Getting frames in**

| Tool | What it does |
| --- | --- |
| `open_clip` | Read from a clip |
| `open_screen` | Read from a shared screen |
| `submit_image` | Hand over a single image |

**Asking what is there**

| Tool | What it does |
| --- | --- |
| `read_perception` | The [perception record](/docs/concepts/perception) |
| `read_text` | Recognised text with its reading order |
| `engine_report` | Budget, degrade level and counters |
| `model_support` | Whether a network's operations are available |

**Space**

| Tool | What it does |
| --- | --- |
| `submit_world` | Pose, planes, anchors and light |
| `submit_world_mesh` | The scanned geometry |
| `floor_plane` | Which surface is the floor |
| `place_on` | Put a footprint on a surface, and what is left |
| `measure_between` | Distance, with the error its inputs carried |
| `path_across_world` | A route across scanned geometry |
| `align_shared` | The transform between two devices' origins |
| `screen_point` | Where a world point lands on screen |

**Marking and recall**

| Tool | What it does |
| --- | --- |
| `annotate` | Leave a mark in the scene |
| `remember` | Keep something worth recalling |
| `search_memory` | Find it again |

## Spatial questions are answered, not computed by the caller

Because the engine already holds planes and anchors, an agent asks the spatial
question directly rather than fetching geometry and doing trigonometry on it.

That matters for correctness as much as for convenience: `measure_between`
returns the distance with the error bar its inputs carried, which a caller
recomputing from raw points would have to derive and would usually drop.

## Scope is a boundary

A session's scope governs what each tool will answer. The server says so in
its own description, and the check happens at every operation a verb covers
rather than once at connection time.

The verbs a build knows are readable from the ABI, so a host can present them
rather than hard-coding a list:

```c
uint32_t count = goss_scope_verb_count();
const char *name = goss_scope_verb_name(index);
```

A session's scope only narrows. Widening means a new session, so a scope
cannot quietly grow during a conversation.

## Everything stays on the device

No tool here sends a frame anywhere. That is a property of the engine rather
than a promise of the server: there is no network path in the core, so the
server has nothing to send with.

## Writing an agent against it

The same rules the SDKs follow apply:

- Ask `engine_report` rather than timing calls from outside.
- Check `model_support` before offering a model, not after loading it.
- A refusal from scope is a request to the host; a refusal from capabilities
  is a fact about the build. Tell them apart before retrying.
